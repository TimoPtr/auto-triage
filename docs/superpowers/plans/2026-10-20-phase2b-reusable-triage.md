# Knowledge bot phase 2b: triage as a reusable workflow

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Consumers call the triage workflow like the index workflows, with a twenty-line caller, instead of installing the gh-aw template and committing its lock file.

**Architecture:** The template moves to `.github/workflows/triage.md` in this repository with an `on: workflow_call` trigger (inputs `issue-number`, `event-action`, `label`, `config`); its compiled `triage.lock.yml` is committed next to it and checked for staleness in CI. The called workflow checks out this repository at `github.job_workflow_sha`, as `build-index.yml` does, so the scripts match the workflow version. The consumer's `knowledge-triage.yml` owns the triggers (`issues: [opened, labeled]`, `workflow_dispatch`) and passes the event facts as inputs. Decided on 2026-10-20 after verifying that gh-aw v0.89.21 compiles a `workflow_call` template (it drops its role check, which the consumer's trigger now owns).

**Spec:** `/Users/timo/Documents/ha/android/docs/superpowers/specs/2026-10-15-knowledge-bot-design.md` sections 3.1, 3.2, 7.1, 7.2.

## Global Constraints

- The lock file is generated by `gh aw compile` with gh-aw v0.89.21 and never edited by hand; `.yamllint` ignores `*.lock.yml`. The CI job `lock` recompiles and fails on a diff.
- Inputs reach `run:` through `env:`; the caller passes `issue-number`, `event-action` (`opened`, `labeled` or `dispatch`), `label`. The trigger step keeps the digits check and the label removal; `roles: all` is gone with the trigger, so the consumer decides who can trigger by choosing the events.
- Behaviour of the three jobs is unchanged; the test suite stays green (302) with the consistency test pointed at the new path.

## Review Focus

1. A consumer caller that forgets a permission must fail loudly, not post nothing: the called workflow declares what it needs at the job level, and the README lists the four scopes (Task 2 doc, Task 3 README).
2. `workflow_dispatch` on the caller passes `event-action: dispatch` so the trigger step neither filters on a label nor removes one (Task 1 trigger step).
